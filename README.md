# Glowy Agent

AI-агент для X и Threads: исследует, что работает в нише, пишет черновики и планирует публикации.
Эта версия: **Phase 1 + 2 + онбординг (Phase 3) + подключение Threads + тред (исследование, варианты, планирование) + публикация в Threads**. Это фундамент, а не готовый продукт. Ниже честно, что работает, а что нет.

## Что работает

| Часть | Статус |
|---|---|
| Лендинг, вход по email (magic link), оболочка приложения, тёмная и светлая тема | Работает (нужен проект Supabase) |
| Страницы Today, Calendar, Analytics, Settings | Каркас с пустыми состояниями, без данных |
| Схема БД Supabase (24 таблицы, RLS, очередь публикаций с защитой от дублей) | Работает. Проверена тестами на настоящем Postgres |
| Онбординг: 7 вопросов по одному на экране, пропуск, «Назад», сохранение в профиль на каждом шаге, редактирование ответов в Settings | Пройден в настоящем браузере на имитации базы (ответы, пропуск, назад, финальное сохранение, тёмная и светлая темы). На живом Supabase ещё не запускался |
| Подключение Threads: кнопка Connect в Settings, обмен кода на токен, шифрование токена AES-256-GCM, список аккаунтов, отключение | Код написан, типы и логика проверены тестами. **Живой вызов к Threads ещё не делали**, первая проверка за тобой (см. «Подключение Threads») |
| `packages/core`: матрица возможностей X и Threads, скоринг постов, расчёт паттернов, лимиты символов, оценка стоимости X API, повторы и идемпотентность публикаций, интерфейс `SocialProvider` | Работает. 20 тестов |

| Тред: кнопка New thread, лимит 5 в сутки (считает база), паттерны, 3 варианта поста с советами по живому контенту, рекомендованное время, планирование | Код, БД и экран проверены тестами и в браузере на имитации. **Живой прогон с Claude и Threads ещё не делали** (см. «Тред») |
| Публикация по расписанию (`publish-due` + cron) | Код написан, типы и логика проверены. Живой пост ещё не публиковали |
| Кэш статусов и данных на главной | Работает: между страницами повторных запросов к базе нет |

## Чего ещё нет

- Подключение X (OAuth), сбор метрик опубликованных постов, автоматическое обновление токена Threads (токен живёт 60 дней, срок обновления уже записывается, но задачи, которая обновляет, пока нет), отмена запланированного поста из интерфейса, картинки к постам
- Исследование ниш, выделение паттернов, генерация черновиков (Phase 4–5). Алгоритм описан в анализе, в коде пока только скоринг и расчёт паттернов в `packages/core`
- Stripe, триал, подписки (Phase 7). Нужно юрлицо в стране, которую поддерживает Stripe
- Autopilot, Electron
- Реализации `SocialProvider` для X и Threads. Заглушек нет сознательно: имитировать интеграции нельзя

Вход через X и Threads как способ логина не делали: для публикации нужна отдельная авторизация с правами на постинг, поэтому аккаунты подключаются отдельным шагом в Settings.

## Что нужно на компьютере

Node.js 20 или новее (проверить: `node -v`). Установка с https://nodejs.org (версия LTS).

## Запуск по шагам

### 1. Установка зависимостей

```bash
cd growth-agent
npm install
```

### 2. Проект Supabase

1. Зарегистрируйся на https://supabase.com и создай проект (регион выбери ближе к себе, пароль БД сохрани).
2. Открой **SQL Editor**, нажми **New query**, вставь целиком содержимое файла `supabase/migrations/0001_init.sql` и нажми **Run**. Должно пройти без ошибок.
3. Открой **Authentication → URL Configuration**:
   - Site URL: `http://localhost:5173`
   - Redirect URLs: добавь `http://localhost:5173/app`
4. Открой **Project Settings → API** и скопируй `Project URL` и ключ `anon public`.

### 3. Переменные окружения

Создай файл `apps/web/.env.local` по образцу `.env.example` в корне:

```
VITE_SUPABASE_URL=https://ТВОЙ-ПРОЕКТ.supabase.co
VITE_SUPABASE_ANON_KEY=ТВОЙ-ANON-КЛЮЧ
```

Ключ `service_role` сюда **не вставляй** никогда: он обходит все защиты.

### 4. Запуск

```bash
npm run dev
```

Открой http://localhost:5173. Введи email на странице входа, перейди по ссылке из письма: попадёшь в приложение.
Бесплатный встроенный почтовый сервис Supabase ограничен по числу писем в час. Для регулярной разработки позже подключи свой SMTP.

## Проверки

```bash
npm run typecheck   # типы во всех пакетах
npm test            # тесты core (35), БД (23), функции подключения (21), signed_request (10), тред (17)
npm run build       # production-сборка веб-приложения
```

Тесты БД запускают настоящую миграцию в Postgres внутри Node и проверяют: пользователь видит только свои данные, токены недоступны клиенту, дубль публикации невозможен, один и тот же пост не забирается в работу дважды.
Роли и схему `auth` Supabase в тестах эмулирует заглушка. Поэтому один раз стоит убедиться на реальном проекте, что миграция применилась без ошибок (шаг 2).

## Структура

```
apps/web/            веб-приложение (React, Vite, TypeScript, Tailwind v4)
packages/core/       логика без UI: типы, возможности платформ, скоринг, лимиты, повторы

```

## Подключение Threads

Предварительно в Meta должно быть готово: приложение с use case «Access the Threads API», ты добавлен как Threads Tester и принял приглашение в Threads (Настройки аккаунта → Website permissions).

### 1. Вторая миграция

В Supabase SQL Editor выполни содержимое `supabase/migrations/0002_oauth_states.sql` (так же, как `0001`).

### 2. Секреты

Project Settings → Edge Functions → Secrets. Должны быть три, ты их уже добавил: `THREADS_APP_ID`, `THREADS_APP_SECRET`, `TOKEN_ENCRYPTION_KEY`.
`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` Supabase подставляет в функции сам. Если это не так, функция вернёт ошибку со списком недостающих секретов.

Для работы на своём компьютере больше ничего не нужно. Когда выложишь приложение на домен, добавь секрет `APP_URL` (например `https://app.example.com`), иначе после подключения пользователя вернут на `http://localhost:5173`.

### 3. Выложить функции

В папке проекта (нужен Node.js, Supabase CLI ставится как dev-зависимость):

```bash
npm install supabase --save-dev
npx supabase login
npx supabase link --project-ref ТВОЙ_REF
npx supabase functions deploy threads-connect-start
npx supabase functions deploy threads-oauth-callback --no-verify-jwt
npx supabase functions deploy threads-deauthorize --no-verify-jwt
npx supabase functions deploy threads-data-deletion --no-verify-jwt
```

`--no-verify-jwt` у трёх последних функций обязателен: в них Meta и браузер приходят без токена приложения. Callback защищает одноразовый `state`, две другие функции проверяют подпись `signed_request` секретом приложения.

### 4. Адрес возврата в Meta

Meta → твоё приложение → Use cases → Customize (Access the Threads API) → Settings. Форма требует заполнить все три поля (подставь свой `ТВОЙ_REF`):

```
Redirect Callback URLs:        https://ТВОЙ_REF.supabase.co/functions/v1/threads-oauth-callback
Deauthorize Callback URL:      https://ТВОЙ_REF.supabase.co/functions/v1/threads-deauthorize
Data Deletion Request URL:     https://ТВОЙ_REF.supabase.co/functions/v1/threads-data-deletion
```

Первый адрес должен совпадать символ в символ. Если форма пишет, что URI переадресации не указан, нажми Enter после ввода адреса, чтобы он превратился в «плашку», затем сохрани.
Формат запроса отзыва доступа для Threads в документации отдельно не описан: функция принимает стандартный `signed_request` Meta. Проверь первый реальный вызов в логах.

### 5. Проверка

1. `npm run dev`, войди в приложение, открой Settings.
2. Нажми Connect у Threads, разреши доступ в окне Threads.
3. Тебя вернёт в Settings, под Threads появится `@твой_username` со статусом Connected.

Если что-то пошло не так, приложение покажет причину на странице. Подробности смотри в Supabase: Edge Functions → выбранная функция → Logs. Токены и секреты в логи не пишутся.

Запрашиваются права `threads_basic`, `threads_content_publish`, `threads_manage_insights`. Права на поиск по публичным постам добавим после одобрения Meta: изменение набора прав потребует от пользователей переподключиться.

## Тред

Тред — один проход агента: исследование тем из онбординга → паттерны → три варианта одного поста → рекомендованное время → публикация. В сутки доступно 5 тредов (по часовому поясу пользователя), лимит занимает база атомарно. Неудачный тред лимит не тратит.

### Что нужно для работы

1. Миграция `supabase/migrations/0003_agent_threads.sql` в SQL Editor.
2. Секреты Edge Functions: ключ модели (`ANTHROPIC_API_KEY`, либо `LLM_API_KEY` + `LLM_MODEL` + `LLM_BASE_URL` для любого OpenAI-совместимого сервиса, например OpenRouter) и `CRON_SECRET` (любая длинная случайная строка, `openssl rand -hex 24`). Необязательно: `ANTHROPIC_MODEL`.
3. Выложить функции:
   ```bash
   npx supabase functions deploy agent-thread-run
   npx supabase functions deploy publish-due --no-verify-jwt
   ```
4. Публикация по расписанию: включи расширения `pg_cron` и `pg_net` (Database → Extensions), подставь `ТВОЙ_REF` и `CRON_SECRET` в `supabase/cron.sql` и выполни его в SQL Editor.

### Что работает честно, а что нет

- **Поиск по публичным постам** Threads отдаёт только после одобрения Meta права `threads_keyword_search`. Без него поиск возвращает только твои собственные посты. Если одобрения нет, тред использует твои посты (что работает именно у тебя) или, если их нет, только ответы онбординга, и пишет об этом в карточке.
- **Лайков и просмотров чужих постов API не даёт.** Поэтому «хайповость» определяется иначе: сравниваются посты из выдачи TOP (ранжирование Meta) с постами из RECENT по тем же темам, и паттерном считается признак, который в TOP встречается заметно чаще. Это сигнал ранжирования, а не подсчёт лайков.
- **Время публикации**: сначала по твоим лучшим постам, потом по времени постов из TOP, иначе типовые окна активности (карточка подписывает, какой источник использован).
- **«Живой контент»**: модель не знает твой день, поэтому не выдумывает цифры. Она вставляет `[[плейсхолдер]]` и подсказывает, что добавить (реальное число, закулисье, скриншот, повод из новостей). Пост с незаполненным плейсхолдером запланировать нельзя.
- Тексты чужих постов в базу не сохраняются: они используются только в запросе к модели.
- Публикация сейчас только текстовая, только Threads.

## Принятые решения (можно поменять)

- **Веб вместо Electron.** Autopilot всё равно должен работать на сервере, а Electron добавляет подпись, автообновления и сложности с OAuth. Оболочку можно добавить позже поверх того же кода.
- **Компоненты в стиле shadcn/ui написаны вручную**, а не через CLI shadcn: Button, Input, Badge на `class-variance-authority` и Tailwind. Остальные добавим по мере надобности.
- **Токены соцсетей** хранятся зашифрованными приложением, а клиентские роли не имеют к таблице никакого доступа.
- **Тексты чужих постов не хранятся**: только ID, метрики и производные признаки.
- **Цены и лимиты API** (`packages/core/src/capabilities.ts`, `limits.ts`) собраны из сторонних обзоров на 19.11.2026. Сверь их в X Developer Console и документации Meta до запуска исследования.
